# 《Agent Harness Engineering: A Survey》论文解读

论文原文：[Agent Harness Engineering: A Survey](https://picrew.github.io/LLM-Harness/main.pdf)

## 一、核心结论

这篇论文的真正贡献不只是提出了一个 ETCLOVG 七层分类法，而是试图改变我们解释 Agent 性能的方式：Agent 的行为并非只由模型能力决定，而是模型与外围执行系统共同构成的闭环结果。因此，一个 benchmark 分数应被视为“模型—harness 组合”的属性，不能脱离工具格式、上下文策略、运行环境、验证器和恢复循环而简单归因给模型。

论文把 **agent harness** 定义为：把模型调用转化为有边界、有状态、可调用工具、可恢复、可观察、可验证、受治理约束的长期多步执行系统。它研究的不是基础模型、单个 prompt 或普通 API wrapper，而是围绕模型运行的完整工程基础设施。

论文属于实践导向的综述与系统映射研究，不是提出新模型并进行统一对照实验的实验论文。其证据来自学术论文、benchmark、170+ 个公开项目、协议文档和公司工程报告。作者引用了一些“固定模型、改变 harness 后性能显著变化”的结果，例如 Terminal-Bench 2.0 从 52.8% 提升到 66.5%，以及某些模型在改变编辑工具格式后最高约 10 倍的提升。但这些数字来自被引用工作，最强证据又主要集中于 coding agent，不能推广为“harness 在所有任务中都比模型更重要”。

## 二、从 Prompt 到 Harness 的概念扩展

论文用三个逐步扩大的工程范围建立研究对象：

1. **Prompt engineering**：设计单次模型调用的指令、示例、格式和推理模板。
2. **Context engineering**：管理每一步模型可见的信息，包括检索文档、历史交互、记忆、排序、过滤和压缩。
3. **Harness engineering**：把 prompt 和 context 纳入完整执行闭环，进一步管理工具、环境、状态、编排、监控、验证、权限和人工审批。

这一区分承担了重要的论证功能：上下文工程决定模型“能看到什么”，但不能决定动作“在哪里执行、有什么权限、如何判错、如何恢复”；这些问题共同构成 harness 工程。

## 三、ETCLOVG 七层框架

论文把七层分为四个结构核心层和三个控制平面。E、T、C、L 负责让任务运行起来；O、V、G 负责观察、判断和约束整个系统。

| 层 | 核心问题 | 论文归纳的主要内容 |
|---|---|---|
| E：Execution | 动作在哪里执行，如何隔离、重置并复现 | 托管 sandbox、computer-use 环境、代码 sandbox、框架内置 runtime、浏览器环境、OS 权限边界、sandbox 抽象层。结论是不存在普适隔离方案，必须按威胁模型、保真度、成本和部署方式选择。 |
| T：Tooling | Agent 如何发现、理解、选择和调用能力 | Function Calling、MCP、A2A、OpenAPI、AGENTS.md 等接口；工具检索与路由；工具增强训练；长会话中的状态与错误管理。工具越多不一定越好，过大的工具菜单会占用上下文并增加选择错误和攻击面。 |
| C：Context | 每一步模型看到什么，信息如何跨时间保存 | 短期 active context、中期 session state、长期 persistent memory、压缩与按需检索。论文区分单次输入过长导致的 context rot 与 100+ turns 后任务状态逐渐错位的 context drift，并认为后者不能只靠扩大窗口解决。 |
| L：Lifecycle | 任务如何跨调用、失败、会话和交接持续推进 | 单 Agent 内循环、多 Agent 编排、issue-to-PR 全生命周期；stateless replay、stateful 与 hybrid 状态。C 关注给模型看的信息，L 关注 checkpoint、pending task、retry、工件和控制流。 |
| O：Observability | 系统做了什么、为何失败、成本多少 | Trace、span、工具调用、token、延迟、异常、成本归因和可靠性工程。关键缺口是“看得到”与“判断得了”脱节：论文引用的调查中，89% 团队使用 observability，但只有 52.4% 做 offline evaluation。 |
| V：Verification | 如何公平、可复现地判断一次执行 | 五阶段 task-to-feedback 生命周期：任务与 benchmark grounding；执行前 readiness；受控 rollout 与 trace 捕获；结果、轨迹和 evaluator 三层判断；持续回归与部署反馈。评价对象不只是最终答案，还包括路径是否合规、失败归因是否可信。 |
| G：Governance | Agent 可以做什么、谁授权、如何审计 | 权限与身份、生命周期 hooks、信息流控制、组件加固、声明式 constitution、审计和人工批准。治理不是最后加一个安全过滤器，而是覆盖工具调用前后、状态传播和跨主体委托的控制平面。 |

七层的承接关系也有意安排：E 提供物理执行面，T 连接外部能力，C 管理模型的信息投影，L 组织状态和流程；运行之后，O 产生 trace，V 将 trace 转化为判断与回归反馈，G 则约束所有层的权限和责任。

## 四、170+ 项目的系统映射

作者从既有综述与 benchmark、GitHub 搜索、项目清单与包注册表、公司工程博客和 release notes 四类来源收集候选项目。纳入条件是：公开可查、存在具体 harness 机制、至少能有证据地映射到一个 ETCLOVG 层。编码允许多标签，但主层表示项目最核心的机制，次层必须是独立能力而非附带依赖。

聚合结果显示：

- E、T、L、V 的公开覆盖最密集，因为代码、浏览器、终端和 computer-use agent 都必须具备执行环境、工具契约、控制循环和可重复评价。
- C/Memory 很常见，但通常嵌入大型框架，独立记忆组件相对少。
- O 和 G 的开源覆盖较薄，更多存在于商业平台、SDK 和工程博客中，说明运营控制、合规和治理比 runtime 与 benchmark 成熟得晚。
- 完整系统越来越跨层组合 sandbox、工具协议、编排、trace、评价和权限，说明 harness 是集成系统，而不是七个可独立安装的插件。
- 层间边界反复出现五个缺口：跨工具互操作、成本归因、失败恢复、多仓库编排、人类—Agent handoff。

这套映射只能看作“可见生态地图”，不是生产系统普查。语料偏向英文、GitHub、开源和 coding agent；闭源系统与非编程场景被低估。项目未被映射到某层，只能说明“公开证据不足”，不能说明该能力不存在。编码还采用单一主编码者加作者审查，没有正式报告多编码员一致性。

## 五、作者最终提炼的三个系统矛盾

### 1. 成本—质量—速度三难

更真实的环境、更强的 sandbox、更深的 trace、更严格的治理和更完整的验证通常能提高安全性与可诊断性，却会增加启动延迟、推理开销、存储、标注和恢复成本。工程问题不是单独追求最高质量，而是决定哪些检查同步执行，哪些放入离线回归，哪些风险值得启动昂贵的恢复路径。

### 2. 能力—控制权衡

更多工具、更持久的记忆和更宽松的执行权限能扩大 Agent 的任务范围，同时也增加工具选择错误、prompt injection、记忆污染、隐私泄露和误操作的 blast radius。能力扩张必须与身份、权限、来源、审计和人工批准共同设计。

### 3. Harness coupling problem

七层存在强耦合，局部优化可能造成全局退化：运行环境的依赖和 reset 语义会改变评测分数；工具描述会消耗上下文并改变模型行为；trace 只有同时携带身份与权限状态，才能成为治理证据；评价指标又会反过来塑造重试和恢复策略。因此，prompt、工具、memory、sandbox、verifier 或 monitor 的修改都应当作为“系统修改”测试。

## 六、论文的论述思路

全文采用“先拆解、再重组”的论证策略：

```text
长程 Agent 的可靠性问题
        ↓
固定模型、改变 harness 也会改变表现
        ↓
模型中心的研究语言不足以解释外围系统
        ↓
划定 harness 的功能边界
        ↓
提出 ETCLOVG 七层分类法
        ↓
用公开项目收集与编码支撑分类的覆盖面
        ↓
按 E → T → C → L → O → V → G 逐层展开
        ↓
重新合成成本、控制与耦合问题
        ↓
提出五类未来研究议题
```

各阶段承担的功能如下：

1. **引言提出问题并给出初步经验依据**：Agent 已从聊天走向仓库、浏览器、终端和企业软件，可靠性依赖上下文、工具、状态、恢复、验证和权限。固定模型而调整 harness 的案例，用来证明 harness 至少是一个可测量的实验变量。
2. **历史回顾构造“工程表面外扩”的趋势**：从 ReAct 单循环，到工具调用、多 Agent、benchmark，再到显式的 harness engineering，为 prompt → context → harness 的概念扩展制造历史必然性。
3. **定义边界后提出分类**：先说明哪些系统属于研究对象，再把 E/T/C/L 设为结构层、O/V/G 设为控制层，避免把所有外围软件都含混地称为 harness。
4. **公开编码协议增强可信度**：项目收集与多标签编码使分类法不只是作者凭经验拼出的目录，但它提供的是覆盖性与可见性证据，不是因果验证。
5. **七层章节逐层铺陈工程事实**：每章基本采用“定义问题—分类系统—比较机制与权衡—提出缺口”的模板，并把单层难题不断推向其他层。
6. **跨层综合完成中心论证**：第 10—11 章把前面人为拆开的七层重新组合为闭环控制系统，说明很多故障发生在接口处，任何单层都不能独立保证可靠性。
7. **未来议程从耦合问题自然推出**：运行环境安全与规模化、长期状态可靠性、trace-native 失败诊断、标准 handoff、模型变强后的 harness 自我简化，分别对应前文反复出现的系统瓶颈。

## 七、批判性评价

论文的优点是：概念边界清楚，能把分散在 sandbox、memory、tool use、observability、evaluation 和 security 社区中的问题放进同一系统视角；它也主动区分结构层和控制层，并把 evaluation 从排行榜分数改写为质量控制反馈循环。这种“闭环控制系统”视角对工程实践很有解释力。

但它仍有明显限制：

- 中心因果命题尚未被统一实验充分证明。若干固定模型的成功案例只能证明 harness 会影响结果，不能证明它普遍决定性能上限。
- 证据质量没有统一加权，同行评审论文、预印本、公司博客、README、GitHub stars 和项目自报数字被并置使用，不能直接横向比较。
- ETCLOVG 很实用，但并非严格正交的本体：E 按 workload 分类，C 按时间尺度分类，L 按组织层级分类，O/V/G 按功能分类；浏览器环境、hooks 和完整框架往往天然跨层。
- 三个跨层矛盾主要是概念综合，尚缺形式化模型、跨项目统计或因果实验。
- Trace-native failure attribution 是合理方向，但论文没有证明 trace 足以稳定地区分模型、工具、context、sandbox、orchestration、benchmark 和 evaluator 的责任；很多失败本来就是多层共同作用。
- 分类法目前是描述性的，不是已经验证的规范性架构标准。作者也承认，下一步需要把它转化为真正能够指导设计取舍的框架。

## 八、五个未来问题

1. 如何在安全性、规模化和可移植性之间选择容器、microVM、OS 权限边界、桌面 VM、浏览器环境或 learned surrogate。
2. 如何把 context management 重新表述为 state estimation，度量压缩、检索和遗忘造成的信息损失与状态偏差。
3. 如何以 trace 为主要评价对象，完成轨迹质量判断、失败归因，并自动把生产异常转成 regression case。
4. 如何建立跨 Agent、工具、sandbox、evaluator 和人类的 handoff contract，使交接同时携带意图、约束、权限、工件、来源、预算、风险、trace 和未决决策。
5. 模型变强后，如何通过 model×harness 因子实验、消融、shadow/A-B 测试和自动搜索，识别不再必要的 scaffolding，并持续简化系统。

## 九、一句话理解

这篇论文把 Agent 可靠性从“模型够不够聪明”的问题，改写成“整个闭环系统能否让能力在受控环境中被正确执行、观察、验证、恢复和治理”的问题。
