# 五个开源 Agent 仓库的指令遵从性形式化分类与代码证据

日期：2026-08-29
研究对象：AutoGen、Cline、MetaGPT、OpenHands、browser-use
方法与实验记录：[研究计划](./17_五仓库指令遵从性静态分析计划.md)、[实验记录](./18_五仓库指令遵从性静态分析实验记录.md)

## 1. 结论口径

本报告把“指令遵从机制”限定为：能改变 agent 所见规范、候选输出、可调用动作、可访问资源、执行前裁决、执行后验证或恢复状态的代码路径。它不把仓库里所有安全、校验、日志或 prompt 都算作指令遵从。

对指令集合 \(I\)、环境状态 \(s\)、模型提议 \(p\)、动作 \(a\) 和轨迹 \(\tau\)，理想遵从性质写为：

\[
\forall \tau\in Traces(\mathcal H,I):\ Sat(\tau,I)=\top.
\]

静态代码通常不能证明这个全称命题。本轮实际检查四种逐级增强的代码效果：

\[
\begin{aligned}
INDUCE &: \Pr[p\models I\mid prompt']>\Pr[p\models I\mid prompt],\\
CONSTRAIN &: Proposals(prompt',schema)\subset Proposals(prompt),\\
ENFORCE &: Executable(s,C)\subset Executable(s),\\
DETECT &: Violation(\tau,I)\rightarrow signal/recover/audit.
\end{aligned}
\]

`INDUCE` 只改变模型概率；`CONSTRAIN` 缩小可表达提议；只有在不可绕过的执行入口拥有裁决时才记为 `ENFORCE`；`DETECT` 若不驱动阻断或恢复，不能撤销既有副作用。

每个机制统一抽象为：

\[
g=(L,T,X,Q,D,F,B,E),
\]

分别表示生命周期 (L)、触发条件 (T)、受控对象 (X)、可信主体 (Q)、状态与裁决 (D)、副作用 sink/失败语义 (F)、旁路与边界 (B) 和证据等级 (E)。为回答“是否专注于指令遵从”，另加焦点编码：

- **D（direct）：**代码或产品语义直接表达用户指令、规则、批准、任务完成或冲突优先级；
- **E（enabling）：**不是以 instruction following 命名，但为确定性遵从提供能力、资源或结构边界；
- **A（adjacent）：**只改善一般安全、鲁棒性、观测或 UX，本报告作为边界项而不计入核心机制。

## 2. OpenHands：当前仓库是控制前端，不是执行器

固定提交：`f26d734a848297d8dcf460b0bb739174e76511f0`。

当前 `OpenHands/OpenHands` 已是 Agent Canvas。README 与 `AGENTS.md` 明确把 agent、tool、conversation、workspace 和 Agent Server 的实现归到外部 `OpenHands/software-agent-sdk`。所以本节能证明“Canvas 发出了何种策略与用户裁决”，不能证明外部 server 完整执行了它们。

### OH-1　初始指令与 skill 上下文装配（D；L0–L2；INDUCE/CONSTRAIN；E2）

实现锚点：`src/api/agent-server-adapter.ts::{buildInitialMessage,buildBundledSkills,buildAgentContext}`；测试：`__tests__/api/agent-server-adapter.test.ts`、`src/api/agent-server-adapter.test.ts`、`__tests__/utils/skill-enablement.test.ts`。

`buildInitialMessage` 把 query 与 `conversationInstructions` 去空后用两个换行连接，作为同一个 `role=user, run=true` 消息发送；它没有在客户端建立两者的优先级。`buildAgentContext` 将用户/项目 skill、按 allow-list 启用的 bundled skill、显式调用的 catalog skill 和运行时服务 suffix 发送给 SDK；显式调用可覆盖 catalog enablement，`disabled_skills` 同时传给后端以排除用户/项目 skill。

形式化为：

\[
M_0=User(trim(q)\Vert trim(c)),\qquad
Skills=(S_{user}\setminus Disabled)\cup Enabled_{catalog}\cup Invoked.
\]

它决定进入上下文的规范集合，但 server 如何排序、触发和注入 skill 在外部仓库。旁路包括 profile 路径由 server 重建 agent context、用户可以禁用 skill、显式调用会临时覆盖 catalog allow-list；因此这是上下文约束，不是执行强制。

### OH-2　工具能力装配（D/E；L0、L4；CONSTRAIN；E2）

实现锚点：`src/api/agent-server-adapter.ts::{shouldIncludeTool,getAgentTools,buildStartConversationRequest}`；测试：`__tests__/api/agent-server-adapter.test.ts`。

Canvas 构造默认工具集；`browser_tool_set` 同时受 `VITE_ENABLE_BROWSER_TOOLS` 和 server capability 约束，`task_tool_set` 还要求 `enable_sub_agents=true`。配置工具只有通过 `shouldIncludeTool` 才进入请求；OpenHands agent 另获得两个 client tools，ACP agent 不获得。

\[
Tools'=Defaults\cup\{browser\mid env\land available\}
\cup\{task\mid subagent\_enabled\land available\}\cup Configured'.
\]

这是能力暴露面缩减；实际 dispatcher 是否拒绝未声明工具仍由外部 server 决定。默认工具本身总是加入，配置项不是严格最小权限 allow-list。

### OH-3　风险分析与确认策略映射（D；L0、L5；AUTHORIZE；E2）

实现锚点：`src/api/agent-server-adapter.ts::{getConversationConfirmationPolicy,getConversationSecurityAnalyzer,buildStartConversationRequest}`、`src/services/settings.ts::DEFAULT_SETTINGS`；测试：`__tests__/api/agent-server-adapter.test.ts`。

映射是确定性的：

\[
Policy=
\begin{cases}
NeverConfirm,& confirmation\_mode\neq true;\\
ConfirmRisky(HIGH,confirm\_unknown=true),& analyzer=llm;\\
AlwaysConfirm,& otherwise.
\end{cases}
\]

分析器可映射为 LLM、pattern 或 policy-rail。关键默认是 `confirmation_mode=false`，即 `NeverConfirm`。客户端只把 policy/analyzer 放入 start payload，风险分类、pending action 保存和副作用前阻塞均不在本仓库；因此只能证明授权协议配置，不能证明完整调解。

### OH-4　确认状态、风险展示与接受/拒绝通道（D；L5；AUTHORIZE/AUDIT；E1）

实现锚点：`src/hooks/use-agent-state.ts::mapExecutionStatusToAgentState`、`src/components/shared/buttons/conversation-confirmation-buttons.tsx::ConversationConfirmationButtons`、`src/hooks/mutation/use-respond-to-confirmation.ts`、`src/api/event-service/event-service.api.ts::respondToConfirmation`。

server 的 `WAITING_FOR_CONFIRMATION` 被映射为 UI 等待态；Canvas 从最新 agent event 读取 `security_risk`，呈现高风险警告，并向 conversation-scoped endpoint 发送 `{accept:boolean}`。Cloud 路径使用 conversation runtime host 与 session API key，本地路径使用 typed client。

边界很重要：请求没有在客户端携带待批准 action ID，而是依赖 server 当前 pending state；`awaitingAction` 实际选取“最新 agent event”，不保证它就是 ActionEvent；前端在请求成功前就把 event ID 写入 `submittedEventIds` 隐藏按钮，mutation 错误没有在该 hook 内恢复 ID。安全性最终取决于 server 对 session、conversation、pending action 与请求的绑定。

### OH-5　迭代、stuck 与 worktree 请求（D/E；L0、L6、L8；CONSTRAIN/ISOLATE/RECOVER；E2）

实现锚点：`src/api/agent-server-adapter.ts::buildStartConversationRequest`、`src/api/conversation-service/agent-server-conversation-service.api.ts`；测试：`__tests__/api/agent-server-adapter.test.ts`、`__tests__/api/agent-server-conversation-service.test.ts`。

Canvas 默认发送 `max_iterations=500`（或用户值）、`stuck_detection=true`、`worktree=true`，并限定 workspace working directory。形式上限制运行长度并请求每会话 Git 变更隔离：

\[
steps\le max\_iterations,\qquad Worktree(child,parent)=separate\_git\_checkout.
\]

但 worktree 不是 OS capability sandbox；README 的本地 npm/source 路径明确警告 agent server 直接在主机运行并拥有完整文件系统访问。用户也可选择 `worktree=false`。真正 stuck 检测与终止在外部 SDK。

### OH-6　子会话参数验证、隔离选择与降级（D/E；L4、L6、L8；VALIDATE/ISOLATE/RECOVER；E2）

实现锚点：`src/services/child-conversation-launch.ts::{validateParams,parentSupportsWorktree,launchLocalChild}`；测试：`__tests__/services/child-conversation-launch.test.ts`。

客户端拒绝空 task、未知 target/isolation、local target 携带 repository/branch、cloud target 携带 isolation，以及无 repository 的 branch。local 默认 `worktree`，cloud 声明独立 sandbox。

\[
Valid(x)=Target(x)\land Isolation(x)\land ArgsCompatible(x)\land task\neq\epsilon.
\]

最关键的失败语义是显式 fail-open：父 workspace 无法创建 worktree，或 worktree 创建失败但 shared 重试成功时，子会话仍在父目录启动；返回值带 `isolation="shared"` 和冲突警告。也就是说 availability 优先于原 isolation 意图：

\[
worktree\_failure\Rightarrow retry(shared),
\]

它是透明降级，不是 fail-closed。若两次都失败则报告原始 worktree 错误。

### OH-7　非幂等子会话调用的 replay ledger（E；L5、L8；VALIDATE/AUDIT；E2）

实现锚点：`src/services/child-conversation-launch.ts::{claimToolCall,handleLaunchChildConversationAction}`；测试：`__tests__/services/child-conversation-launch.test.ts::ignores a replayed tool call`。

以 `(parentConversationId,toolCallId)` 为键在 `localStorage` 声明调用，重复 event 不再启动第二个子会话：

\[
Claim(k)=\begin{cases}deny,&k\in Ledger;\\allow\land Ledger:=Ledger\cup\{k\},&otherwise.\end{cases}
\]

损坏 ledger 会重建；存储满或不可用时继续启动，注释明确接受 replay 风险。因此它防止常见重复副作用，但不是可靠、服务端拥有的幂等键。

### OpenHands 小结

该仓库最直接的尝试是确认策略、用户确认通道、工具/skill 装配和子会话隔离协议。它的强项是把控制意图显式编码成 typed payload 与状态；最大边界是执行器已迁出仓库，默认确认关闭，本地部署可无 sandbox，worktree 失败会降级到 shared。静态证据不支持“OpenHands 在所有工具前完整调解”的结论。

## 3. browser-use：在专用浏览器与文件 sink 上有较多确定性控制

固定提交：`2e32d260341fae39c80bc8529ec174bad91e7672`。

### BU-1　system prompt、任务标签与逐步状态构造（D；L1–L3；INDUCE；E1）

实现锚点：`browser_use/agent/prompts.py::{SystemPrompt,AgentMessagePrompt}`、`browser_use/agent/message_manager/service.py::{MessageManager,create_state_messages}`、`browser_use/agent/system_prompts/*.md`。

框架把任务放进 `<user_request>`，把历史、agent state、browser state、read state 与 page-specific actions 分区；system prompt 规定规划、完成检查、动作顺序与最终 `done` 语义。`override_system_message` 可完全替换默认模板，`extend_system_message` 可追加文本。

\[
Prompt=System\Vert User(<user\_request>,<history>,<browser\_state>,\ldots).
\]

这是最直接的“让模型遵从指令”尝试，但只属 `INDUCE`。网页 DOM 与用户任务处在同一个 UserMessage 的不同标签中；在固定核心 prompt 路径搜索不到专门的 prompt-injection/source-trust 仲裁器。自定义 override 还能移除默认完成规则。

### BU-2　动态动作 schema、参数验证与动作数上限（D/E；L3–L4；CONSTRAIN/VALIDATE；E2）

实现锚点：`browser_use/tools/registry/service.py::{Registry.action,execute_action,create_action_model}`、`browser_use/tools/registry/views.py::{ActionModel,ActionRegistry}`、`browser_use/agent/service.py::get_model_output`；测试：`tests/ci/infrastructure/test_registry_core.py`、`test_registry_validation.py`、`test_registry_action_parameter_injection.py`。

注册器从函数签名创建 Pydantic 参数模型；LLM 输出必须匹配动态 union，`ActionModel` 设 `extra='forbid'`；executor 再用 action 的 `param_model` 验证参数，未知 action 拒绝。`get_model_output` 还把动作列表截断到 `max_actions_per_step`。

\[
Execute(name,p)\Rightarrow name\in Registry\land ParamModel_{name}(p)=\top.
\]

`exclude_actions` 在注册期移除能力。domain-filtered custom action 只在 `create_action_model(page_url)` 中隐藏；`execute_action` 不重新检查 `RegisteredAction.domains`，所以直接 registry 调用或陈旧已构造 action 不是完整授权 gate。这一项必须标为“schema 约束 + 参数强制”，不能把 domain filter 表述成 executor 强制。

### BU-3　导航域名/IP 的前置与后置调解（D/E；L4–L7；AUTHORIZE/ISOLATE/RECOVER；E2）

实现锚点：`browser_use/browser/watchdogs/security_watchdog.py::SecurityWatchdog`、`browser_use/browser/profile.py::BrowserProfile`；测试：`tests/ci/security/test_domain_filtering.py`、`test_ip_blocking.py`、`test_mcp_allowed_domains.py`。

SecurityWatchdog 监听 `NavigateToUrlEvent`、`NavigationCompleteEvent`、`TabCreatedEvent`。前置不允许时抛异常阻止导航；redirect 落到不允许域时尝试导航到 `about:blank`；新 tab 不允许时尝试关闭。可形式化为：

\[
AllowURL(u)=Internal(u)\lor DataBlob(u)\lor
[IPRule(u)\land DomainRule(u)].
\]

`allowed_domains` 存在时优先形成 allow-list；否则使用 prohibited list。默认两者为空即允许所有 URL，`block_ip_addresses=false`。`data:`、`blob:` 和特定内部页面总是允许。后置恢复若 CDP navigate/close 失败只记录错误，不会进一步 kill session，属于恢复失败时降级；前置事件路径本身是 fail-closed。

### BU-4　domain-scoped secret、消息脱敏与 password DOM 抑制（D/E；L2、L4、L7；CONSTRAIN/VALIDATE；E2）

实现锚点：`browser_use/tools/registry/service.py::_replace_sensitive_data`、`browser_use/agent/message_manager/service.py::_filter_sensitive_data`、`browser_use/dom/serializer/serializer.py::_build_attributes_string`；测试：`tests/ci/security/test_sensitive_data.py`。

新格式 `{domain_pattern:{key:value}}` 只在当前 URL 匹配时把 `<secret>key</secret>` 替换为真实值；消息进入 LLM 前按所有 secret value 脱敏；password input 的 AX/HTML value 不进入 DOM snapshot。

\[
Reveal(k,u)=\exists d:\ match(u,d)\land k\in Secrets[d].
\]

旧格式 `{key:value}` 为兼容而对所有域可用；缺失 placeholder 只 warning 并保留，初始化时若 sensitive data 存在却没有 allowed domains 也主要发出警告而非阻断。因此它显著缩小 secret 暴露面，但不是默认强制的完整信息流策略。

### BU-5　agent 文件区、上传 allow-list 与下载路径 containment（E；L4–L6；VALIDATE/ISOLATE；E2）

实现锚点：`browser_use/filesystem/file_system.py::FileSystem`、`browser_use/tools/service.py::{upload_file,write_file,read_file}`、`browser_use/browser/watchdogs/downloads_watchdog.py::{_sanitize_download_filename,_is_path_contained}`；测试：`tests/ci/infrastructure/test_filesystem.py`、`tests/ci/security/test_upload_file_containment.py`、`test_download_filename_sanitization.py`。

FileSystem 将 agent 写入限制在 `browseruse_agent_data`，规范化文件名并限制支持扩展；local upload 只能使用明确 `available_file_paths` 或 FileSystem 拥有的 basename，且以 `realpath` 再检查 containment；攻击者控制的 download filename 先取 basename/去 NUL，每个磁盘 sink 再检查 containment。

\[
Write(p)\Rightarrow realpath(p)\preceq realpath(data\_dir),\qquad
Upload(p)\Rightarrow p\in Available\lor p\in Managed.
\]

remote browser 的绝对路径按远端语义传递，不由本地 FileSystem containment 证明；一般 Python process 的其他直接文件 API 也不在此 gate 中。

### BU-6　多动作序列的陈旧页面保护（E；L5–L7；VALIDATE/RECOVER；E2）

实现锚点：`browser_use/agent/service.py::multi_act`；测试：`tests/ci/test_multi_act_guards.py`。

每个动作后，若结果 done/error、注册元数据 `terminates_sequence=true`，或 URL/焦点 target 改变，剩余排队动作停止；`done` 只能作为单独动作。

\[
ChangedPage(a_i)\lor Terminates(a_i)\lor Error(a_i)
\Rightarrow \neg Execute(a_{i+1..n}).
\]

这防止基于旧 DOM index 继续执行，但不判断动作是否符合更高层用户意图。

### BU-7　暂停/停止、步数与连续失败终止（D；L8；RECOVER/CONSTRAIN；E2）

实现锚点：`browser_use/agent/service.py::{_check_stop_or_pause,_force_done_after_last_step,_force_done_after_failure,_get_model_output_with_retry}`；测试：`tests/ci/test_budget_warning.py`、`test_action_loop_detection.py`、`test_beta_agent.py`。

外部 stop callback、`state.stopped` 或 `state.paused` 在 step 与每个 action 前引发 `InterruptedError`；达到最后一步或连续失败阈值时，输出 schema 被缩为只允许 `done`；空 action 重试后仍为空则插入 `done(success=false)`。动作数、失败数和步数是跨步状态。

但 `done.success` 仍是模型自报；强制 `done` 限制后续动作，不证明任务已经满足。`final_response_after_failure` 允许在失败阈值后再生成一次最终响应，是受限恢复而非成功验证。

### BU-8　结构化最终输出（D；L3、L7–L8；CONSTRAIN/VALIDATE；E2）

实现锚点：`browser_use/tools/service.py::use_structured_output_action`、`browser_use/tools/views.py::{DoneAction,StructuredOutputAction}`、`browser_use/agent/service.py::_enhance_task_with_schema`。

用户提供 `output_model_schema` 时，最终 action 被替换为带 Pydantic data 模型的 structured output；工具/LLM provider 的 schema 校验限制形状。形式为：

\[
Final(x)\Rightarrow Schema_{user}(x.data)=\top.
\]

它保证输出结构，不保证数据真实或任务完成；后者仍需观察或 evaluator。

### BU-9　trace judge 是后置测量，不是 gate（D/A；L8；EVALUATE/AUDIT；E1）

实现锚点：`browser_use/agent/service.py::{_judge_trace,_judge_and_log}`、`browser_use/agent/judge.py`。

judge 基于 task、final result、步骤与截图生成 verdict，并附到最后 ActionResult。源码注释明确 verdict **不覆盖** `last_result.success`，遥测同时发送两者。

\[
Judge(\tau)\rightarrow verdict\quad\land\quad success_{agent}:=success_{agent}.
\]

因此它适合离线遵从测量或告警，不能被归类为执行前强制。

### browser-use 小结

browser-use 最强的尝试不是 prompt 本身，而是专用 sink 上的确定性控制：导航 watchdog、Pydantic action/参数验证、secret 域绑定、上传/下载 containment、多动作陈旧状态终止。主要薄弱点是这些控制只覆盖框架拥有的浏览器/文件入口，默认域限制和 IP 阻断关闭，自定义 action 的 domain filter 没有在 executor 重检，网页内容没有独立来源信任层，最终成功仍由模型自报。

## 4. AutoGen：提供可组合原语，但没有统一语义策略层

固定提交：`027ecf0a379bcc1d09956d46d12d44a3ad9cee14`。审计覆盖 Python `autogen-core`、`autogen-agentchat` 和 `autogen-ext`；Studio、示例和 .NET 不在本轮范围。

### AG-1　系统指令、工具循环与结构化输出（D/E；L0–L4、L7；INDUCE/CONSTRAIN/VALIDATE；E2）

实现锚点：`python/packages/autogen-agentchat/src/autogen_agentchat/agents/_assistant_agent.py::{__init__,_call_llm,_process_model_result,_execute_tool_call}`；测试：`python/packages/autogen-agentchat/tests/test_assistant_agent.py`。

调用链为 `on_messages_stream → _call_llm → _process_model_result → _execute_tool_call → Workbench.call_tool`。系统消息改变模型条件分布，`max_tool_iterations` 限制同一回合的工具循环，结构化输出由模型 client/Pydantic 约束。非法 JSON 参数会成为错误结果；默认 `max_tool_iterations=1`。但注册工具无需再次证明与用户意图一致；同一模型响应包含 handoff 与普通工具时，普通工具可能先执行。

### AG-2　Workbench allow-list 与参数 schema（E；L3–L4；CONSTRAIN/VALIDATE；E2）

实现锚点：`autogen_core/tools/_static_workbench.py::{list_tools,call_tool,call_tool_stream}`、`tools/_base.py::run_json`、`tools/_function_tool.py::run`；测试：`test_static_workbench_overrides.py`、`test_workbench.py`、`test_tools.py`。

\[
Call_W(n,x)=
\begin{cases}
Error,&n\notin Names(W)\lor Schema_n(x)=\bot,\\
run_n(x),&\text{otherwise}.
\end{cases}
\]

这对“工具存在且参数成形”构成局部执行约束，不对用户意图构成授权。底层函数、`BaseTool.run_json` 或 executor 可被直接调用；streaming workbench 对工具重命名的列举与调用还有不一致。

### AG-3　消息级 InterventionHandler（E；L1、L4、L8；AUTHORIZE/VALIDATE/AUDIT；E2）

实现锚点：`autogen_core/_intervention.py`、`_single_threaded_agent_runtime.py::_process_next`；测试：`autogen-core/tests/test_intervention.py`。

\[
M'=H_k(\cdots H_1(M)),\qquad H_i(M)=DropMessage\Rightarrow Deliver(M)=\bot.
\]

配置 handler 后，`send/publish/response` 可在 runtime 交付前修改或丢弃消息。默认 `intervention_handlers=None`，而且只覆盖 `SingleThreadedAgentRuntime`；它不内置指令检查，也不支配直接工具或代码执行。publish handler 抛错只记录日志，publisher 不会收到同步拒绝。

### AG-4　CodeExecutorAgent 审批回调（D；L5；AUTHORIZE；E2）

实现锚点：`autogen_agentchat/agents/_code_executor_agent.py::{ApprovalRequest,ApprovalResponse,execute_code_block,_to_config,_from_config}`；测试：`test_code_executor_agent.py`。

\[
Exec(c)\iff approval\_func(c,context).approved=\top.
\]

这是 AutoGen 中最直接的执行前遵从尝试：在该 agent 路径且回调已配置时，拒绝会返回错误且不调用 `CodeExecutor.execute_code_blocks`；回调异常也不会进入 sink。关键默认却是 `approval_func=None` 时自动执行。回调不可序列化，加载配置时被显式重建为 `None`；直接调用 executor 同样绕开审批。因此它是**局部、可选、配置保存后会弱化**的 gate，而不是全局策略层。

### AG-5　本地与 Docker 代码执行边界（E；L6–L7；ISOLATE/VALIDATE/RECOVER；E2）

实现锚点：`autogen_ext/code_executors/local/__init__.py::_execute_code_dont_check_setup`、`docker/_docker_code_executor.py::{start,_execute_command}`；测试：两个 `test_*commandline_code_executor.py`。

本地 executor 检查语言、workspace 内脚本路径、timeout/cancellation，却可用宿主权限执行 Python、shell 和 PowerShell（后者使用 `-ExecutionPolicy Bypass`）；固定提交实现中未找到文档声称的危险命令 sanitizer。Docker executor 把代码放入容器并设置超时，但默认网络未关闭、工作目录为读写 bind mount，还允许额外 volumes、hosts 与 devices。两者都是危害半径约束，不是指令语义授权。

### AG-6　上下文过滤、终止条件与工作流路由（D/E；L1–L4、L7–L8；INDUCE/CONSTRAIN/RECOVER；E2）

实现锚点：`agents/_message_filter_agent.py`、`base/_termination.py`、`conditions/_terminations.py`、`teams/_group_chat/_selector_group_chat.py`、`teams/_group_chat/_graph/_digraph_group_chat.py`；对应 `test_group_chat*.py` 与 `test_termination_condition.py`。

`MessageFilterAgent` 只把指定来源/位置的历史交给 wrapped agent；TerminationCondition 按消息、token、文本、handoff、函数调用、超时或外部信号停止；SelectorGroupChat 和 GraphFlow 约束下一 speaker 与允许路由。它们确定性地管理上下文与生命周期，却在 participant 已完成内部工具调用后才看见 response，不能撤销副作用。Selector 重试耗尽会回退到上一 speaker 或首个参与者。序列化还会丢失 `TextMentionTermination.sources` 和 callable graph condition，使加载后的约束变弱。

### AutoGen 小结

AutoGen 的设计中心是可组合 orchestration primitives。能够形成执行前 `allow/deny` 的机制存在，但需要调用方显式安装并且覆盖面局部；普通工具、直接 executor、其他 runtime 和序列化恢复形成边界。不能从“工具 schema + 工作流图 + 终止条件”推导出全局自然语言指令遵从。

## 5. Cline：本地工具主路径有审批支配，跨执行模式仍有旁路

固定提交：`cea134be06cbb60af4a7341ddc065c3b8be6be86`。

对本地 `AgentTool`，主调用链可概括为：

\[
ModelOutput\rightarrow Normalize\rightarrow Hooks_{pre}\rightarrow Policy
\rightarrow Approval\rightarrow tool.execute\rightarrow Sink.
\]

### CL-1　规则、用户指令、skill 与 workflow 合成（D；L0–L2；INDUCE/CONSTRAIN；E2）

实现锚点：`sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts::composeSystemPrompt`、`runtime/safety/rules.ts`、`extensions/config/user-instruction-config-loader.ts`、`user-instruction-plugin.ts`；测试：配置 loader 与 `runtime-builder.test.ts`。

规则、配置 prompt、语言、工作区/用户指令与 skill 被装配进系统上下文；禁用、歧义或不存在的 skill 会返回错误。但“必须调用 skill”等主要仍是 prompt 描述；配置 watcher 启动异常被空 catch 吞掉，解析失败可能表现为规则缺席。

### CL-2　工具可用性、参数校验与本地 policy（D/E；L0、L3–L5；CONSTRAIN/VALIDATE/AUTHORIZE；E2）

实现锚点：`sdk/packages/core/src/extensions/tools/{presets.ts,definitions.ts}`、`runtime-builder.ts`、`sdk/packages/agents/src/agent-runtime.ts::{prepareToolExecution,requestToolApproval,executePreparedTool}`、`sdk/packages/shared/src/parse/zod.ts`；测试：`agent-runtime.test.ts`、`runtime-builder.test.ts`。

\[
Allow_{local}(t,x)=Exists(t)\land Enabled(t)\land
(AutoApprove(t)\lor Approved(t,x)).
\]

非法 JSON 会形成 `inputParseError` 并跳过执行；内置 wrapper 使用 Zod，但通用 `createTool` 不会自动替所有自定义工具执行 schema 校验。策略显式 `enabled=false` 时拒绝；`autoApprove=false` 时，无回调或回调异常均 fail-closed。反面是未列出的 policy 默认 enabled/auto-approved。plan/yolo/act preset 裁剪模型可见工具，却不能约束后来合并的任意扩展。

### CL-3　计划模式 shell guard（D/E；L4–L6；VALIDATE/AUTHORIZE；E2）

实现锚点：`extensions/tools/command-guard-extension.ts`、`command-guard.ts`；测试：`command-guard-extension.test.ts`、`runtime-builder.test.ts`。

只有 `mode=plan` 且工具名精确为 `run_commands` 时，黑名单扫描器才在 sink 前检查命令，命中后返回 skip。源码自己记录了 `python -c`、嵌套 `bash -c`、quoted/heredoc 等绕过；MCP 别名也不受该精确名称守卫。因此该机制只保证“已识别模式被阻断”。

### CL-4　VSCode 动态审批与 hooks（D；L1、L4–L5、L8；AUTHORIZE/AUDIT/RECOVER；E2）

实现锚点：`apps/vscode/src/sdk/{sdk-tool-policies.ts,SdkController.ts,sdk-interaction-coordinator.ts,hooks-adapter.ts}`、`apps/vscode/src/core/hooks/hook-factory.ts`；测试：`sdk-tool-policies.test.ts`、`sdk-interaction-coordinator.test.ts` 与 agent runtime hook tests。

高风险类别默认需 UI 审批，拒绝会阻止本地 executor；live callback 读取最新设置。`PreToolUse` 只有显式结构化 `cancel/skip` 才阻断，脚本非零、普通异常和 adapter catch 多数 fail-open；`afterTool` 仅能记录或影响后续上下文。diff preview 打不开仍继续审批，因此 preview 是解释辅助而非写入 gate。

### CL-5　MCP、provider 工具与完整调解边界（D/E；L4–L6；AUTHORIZE/ISOLATE；E2）

实现锚点：`extensions/mcp/tools.ts`、`apps/vscode/src/sdk/vscode-runtime-builder.ts`、`agent-runtime.ts` 的 provider 分支。

VSCode 活跃路径会为当前 MCP 工具附加需审批 policy，但通用 MCP wrapper 自身只是 `provider.callTool(...)`，没有独立授权。更关键的是 `executionMode="provider"` 的模型工具被标为本地执行 disabled，模型 provider 在外部完成实际动作；它不进入本地 beforeTool、policy 或 approval。故 CL-2 的支配关系只能限定在 local AgentTool sink，不能外推到 web search、image generation 或其他 provider 能力。

### CL-6　路径、完成与长存进程边界（E/A；L6–L8；VALIDATE/RECOVER/AUDIT；E2）

实现锚点：`extensions/tools/schemas.ts::AbsolutePath`、`executors/{file-read.ts,editor.ts,apply-patch.ts}`、`apps/vscode/src/sdk/vscode-run-commands-tool.ts`、`agent-runtime.ts` 的 completion policy。

`AbsolutePath` 实际只是 `z.string()`；相关 executor 对绝对路径直接接受，未证明 workspace containment。前台命令运行 300 秒可 detach，用户也可选择继续运行，导致工具已返回而进程仍产生副作用；abort 只是尽力终止进程树。若存在 `completesRun` 工具，runtime 会要求一次成功调用；但 `verified`/summary 不做语义证明，而 VSCode route 明确不暴露 completion tool，文本回合即可结束。

### Cline 小结

Cline 在“本地、已注册 AgentTool、明确 policy、未被 hook 异常降级”的条件下具备本轮最清楚的审批调用链；它依旧没有统一的自然语言一致性判定。provider、通用 MCP、绝对路径、黑名单 shell guard、fail-open hook 与 detached process 是必须写进结论的边界。

## 6. MetaGPT：SOP、结构和评审丰富，执行授权与隔离薄弱

固定提交：`11cdf466d042aece04fc6cfd13b28e1a70341b1f`。

### MG-1　需求—TRD—framework 生成/评估链（D；L1–L3、L7–L8；INDUCE/EVALUATE/VALIDATE/RECOVER；E1）

实现锚点：`metagpt/actions/requirement_analysis/{trd,framework}`、`evaluate_action.py`、`metagpt/tools/libs/software_development.py::{write_trd_and_framework,write_framework}`。

RFC243 路径用 LLM 把原始要求展开为 TRD/framework，再由多个评估结果投票形成 `EvaluationData.is_pass`；JSON/Pydantic 失败最多重试，预算与 loop 限制终止。但 `write_framework` 在取得评估值后无条件调用 `save_framework`，所以 `is_pass=false` 仍可能落盘：

\[
Evaluate(f)=false\centernot\Rightarrow \neg Save(f).
\]

这是“评估存在但不支配 sink”的明确反例；也没有专门测试断言该门控。

### MG-2　RoleZero 命令协议与工具映射（D/E；L2–L5；INDUCE/CONSTRAIN/RECOVER；E1）

实现锚点：`metagpt/roles/di/role_zero.py`、`utils/role_zero_utils.py`、`prompts/di/role_zero.py`。

`LLM → parse_commands → _run_commands → tool_execution_map[name](**args)` 要求 JSON 命令数组；解析失败会尝试修复，编辑类 exclusive command 只保留第一个，未知命令或执行异常停止后续动作。执行入口只检查名称是否在 map，并没有统一参数 schema、推荐集合成员检查或人工批准。外部还可直接调用 map 中工具。

### MG-3　ToolRegistry/ToolRecommender 只约束可见性（E；L0、L2、L4；INDUCE/CONSTRAIN；E2）

实现锚点：`metagpt/tools/{tool_registry.py,tool_recommend.py,tool_data_type.py}` 与 `role_zero.py::set_tool_execution`；测试：`tests/metagpt/tools/test_tool_recommend.py`。

推荐器用标签、BM25/LLM 和 schema 控制提供给模型的描述；非法名称被跳过。然而 `RoleZero.set_tool_execution` 无条件把全部 Browser/Editor 方法加入实际 map，`_run_commands` 不复核推荐结果。因而：

\[
Advertised(t)=false\centernot\Rightarrow Executable(t)=false.
\]

### MG-4　ActionNode 结构化输出、review 与 revise（D/E；L3、L7；CONSTRAIN/VALIDATE/RECOVER；E2）

实现锚点：`metagpt/actions/action_node.py::{fill,compile,_aask_v1,review,revise}`；测试：`tests/metagpt/actions/test_action_node.py`。

动态 Pydantic model 对缺失必填字段拒绝、JSON 可修复；unknown 字段只 warning，XML 转换失败可变成 `0`/空集合，raw/single/code fill 绕开完整结构。LLM review/revise 可以修正被评论字段，但不证明自然语言要求满足，也不支配所有下游文件/终端 sink。

### MG-5　消息路由、TeamLeader SOP 与 Plan DAG（D/E；L1–L5、L7–L8；INDUCE/CONSTRAIN/AUTHORIZE/RECOVER/AUDIT；E2）

实现锚点：`schema.py::{Message,Plan,Task}`、`roles/role.py`、`environment/{base_env.py,mgx/mgx_env.py}`、`roles/di/team_leader.py`、`actions/di/write_plan.py`、`strategy/planner.py`；对应 role、plan 与 schema tests。

`send_to/cause_by/watch` 决定消息分发和观察，TeamLeader prompt 诱导 PM→Architect→Engineer 流程；Plan 对任务依赖拓扑排序并能递归重置下游任务。这些是确定性组织状态，不是身份认证。`finish_current_task` 本身不检查 `TaskResult.is_success`；自动 review 才按成功值确认，人工模式只要文本包含 `confirm`，即使代码失败也可完成，`redo` 分支没有实现实际重试。

### MG-6　Terminal、Editor 与代码执行边界（E/A；L4、L6–L8；CONSTRAIN/VALIDATE/RECOVER；E2）

实现锚点：`tools/libs/terminal.py`、`tools/libs/editor.py`、`actions/di/execute_nb_code.py`、`actions/run_code.py`；测试：terminal/editor/notebook tests。

Terminal 只对大小写敏感的 `"run dev"` 和 `"serve "` 两个子串做替换，随后把命令交给持久 shell；没有 allow-list、路径/网络限制或审批。Editor 的 edit/append 路径可在新增 lint 错误时恢复备份，RoleZero 默认启用此能力；普通 Editor 默认关闭，且 `write/create_file`、直接 `awrite`、Terminal/Python 写入都绕开它，路径修复也不提供 containment。Notebook 和 RunCode 支持 timeout、kernel reset、terminate 与结果状态，却在真实 `exec/Popen/kernel` 副作用之后判断，不能算 sandbox。

### MG-7　Reporter/Memory 审计与后置代码审查（D/A；L0–L8；AUDIT/EVALUATE；E2）

实现锚点：`utils/report.py`、`environment/base_env.py::history`、`actions/write_code_review.py`；测试：`tests/metagpt/test_reporter.py`。

Plan、Terminal、Editor、Notebook 等事件可写入 reporter callback 与 memory，代码 review 可生成重写建议；默认 callback 可为空，记录不形成 allow/deny，不是不可篡改审计，也不保证每条副作用都有请求—裁决—结果关联。

### MetaGPT 小结

MetaGPT 最专注的尝试在“保留需求、按 SOP 拆解、结构化交付、评审并重试”。这些机制对格式、计划状态和局部 lint 有效，却没有统一执行前授权、OS sandbox 或 workspace containment。`is_pass=false` 仍保存、推荐工具不支配 map、失败任务可人工确认，是三条最关键的完整调解反例。

## 7. 跨仓库形式化分类

### 7.1 生命周期覆盖

符号：`●` 有直接机制；`◐` 有能力/邻接机制或只覆盖局部路径；`○` 本仓固定提交未找到可归因的实现；`↗` 关键强制层在外部仓库/服务。该表表示**机制位置**，不是质量评分。

| 仓库 | L0 配置 | L1 指令/上下文 | L2 规划/路由 | L3 生成 | L4 动作解析 | L5 授权 | L6 执行隔离 | L7 验证/恢复 | L8 完成/审计 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| AutoGen | ● | ● | ● | ● | ● | ◐ | ◐ | ● | ● |
| Cline | ● | ● | ● | ● | ● | ● | ◐ | ● | ● |
| MetaGPT | ● | ● | ● | ● | ● | ◐ | ○ | ● | ● |
| OpenHands Canvas | ● | ● | ◐ | ↗ | ● | ●/↗ | ◐/↗ | ●/↗ | ●/↗ |
| browser-use | ● | ● | ● | ● | ● | ◐ | ● | ● | ● |

共同模式是 L1 的 prompt/context 与 L3–L4 的 schema/tool protocol 普遍存在；差异主要出现在 L5–L6：是否有真实执行前裁决、它是否默认启用、以及它是否支配所有副作用入口。

### 7.2 作用方式、决策主体与保证形式

| 仓库 | 直接关注点 | 最强可证明局部性质 | 决策主体 | 主要默认/故障边界 |
|---|---|---|---|---|
| AutoGen | 系统消息、可编程 intervention、代码审批、team 终止 | 配置 `approval_func` 时，CodeExecutorAgent 拒绝不进入 executor | 调用方回调/runtime handler | 审批默认无；序列化丢审批；普通工具直通 |
| Cline | rules/skills、mode、tool policy、用户批准、完成协议 | local AgentTool 若 policy 要求批准，则拒绝/审批异常不执行 | runtime policy + 用户/UI + hook | 未列 policy 默认放行；provider/MCP/绝对路径/detach 边界 |
| MetaGPT | 需求→SOP→结构化产物→评审/计划 | Plan DAG 状态与部分 Editor lint rollback | Python 状态机 + LLM reviewer + 人工文本确认 | 无统一授权/沙箱；若干评估不支配 sink |
| OpenHands Canvas | conversation instructions、skills、tool config、风险确认、子会话 | Canvas 能发出 typed confirmation/隔离请求并记录接受/拒绝 | 用户 + 客户端策略，实际执行由外部 SDK/server | confirm 默认 off；本地无 sandbox；worktree 失败退回 shared |
| browser-use | 浏览器动作协议、导航域/IP、secret、文件 containment、停止 | 框架自有导航/上传/下载 sink 上的确定性边界 | watchdog/registry/Pydantic + 配置 | 域/IP 限制默认关；custom action 域过滤未在 executor 重检 |

### 7.3 完整调解判定

对某机制 (g)、sink 集合 (S) 和配置 (C)，定义：

\[
Dom(g,S,C)\equiv \forall a\in S:
Exec(a,C)\Rightarrow Mediated_g(a,C)\land Allowed_g(a,C).
\]

静态审计只在下列窄条件接受 `Dom`：

| 机制 | `Dom` 成立的限定域 | 为什么不能推广 |
|---|---|---|
| AutoGen code approval | `CodeExecutorAgent.execute_code_block` 且 callback 已配置、未序列化恢复 | 直接 executor、普通工具和其他 runtime 不经过它 |
| Cline local approval | local AgentTool 且 policy `autoApprove=false`，执行仍在当前 runtime | provider 在外部执行；MCP wrapper/默认 policy 依赖 host 配置 |
| browser-use navigation/file gates | 框架拥有的导航、local upload/download 与 managed FileSystem sink | 默认配置宽松；自定义 action/远端路径/直接 Python API 不在 gate 中 |
| OpenHands confirmation | 当前仓只能证明 request/response protocol | 真正 action 绑定、TOCTOU 与执行阻断在外部 server |
| MetaGPT | 未找到覆盖通用副作用的机制 | 结构/评审/计划均可被直接执行入口绕过 |

因此五仓都不能支持：

\[
\forall a\in AllSideEffects:\ Exec(a)\Rightarrow Sat(a,I).
\]

更准确的工程图景是“提示诱导 + 候选空间约束 + 若干局部执行 gate + 后置恢复/观测”的组合。

## 8. 研究回答与分类结论

### RQ1：有哪些专注于指令遵从性的尝试？

可以归为六族：

1. **规范注入：**system prompt、conversation instructions、rules、skills、SOP 与角色描述；
2. **上下文和路由治理：**message filter、watch/send_to、speaker/graph、TeamLeader 与子会话；
3. **动作空间治理：**tool allow-list/preset、schema、JSON 命令协议、action registry；
4. **执行前裁决：**AutoGen code approval、Cline local tool approval/hooks、OpenHands confirmation、browser-use navigation policy；
5. **资源与副作用边界：**容器/工作目录、浏览器域/IP、secret、上传下载 containment、lint rollback；
6. **完成、恢复和观测：**termination/iteration、Plan 状态、stuck detection、trace judge、reporter 与 replay ledger。

其中第 1 族主要是 `INDUCE`，第 2–3 族主要是 `CONSTRAIN`，只有第 4–5 族在限定 sink 上可能达到 `ENFORCE`，第 6 族通常是 `DETECT/RECOVER/AUDIT`。

### RQ2：它们在何时生效？

所有仓库都不是单点控制，而是跨 L0–L8 分散生效。prompt 与规则在动作生成前；schema/registry 在提议转为动作时；批准和导航检查紧邻副作用；timeout/lint/redirect 检查处于执行中或执行后；termination/judge/reporter 只影响后续轨迹或观测。越靠后越容易拿到真实执行状态，但越难撤销已经完成的外部副作用。

### RQ3：作用方式如何分类？

决定保证强度的不是标签数量，而是三件事：

\[
Guarantee(g)=Coverage(g)\land Mandatory(g)\land FailClosed(g).
\]

- `Coverage`：是否覆盖目标 sink，而非只覆盖模型可见 schema；
- `Mandatory`：是否存在直接 API、外部 provider、扩展或序列化旁路；
- `FailClosed`：配置缺失、解析失败、网络异常和恢复失败时是否拒绝。

本轮最常见的失效原因依次是：控制只存在于 prompt；可见工具集合与真实执行 map 不一致；控制默认关闭或未列规则即放行；执行器位于外部仓库；后置评估没有支配 sink；失败时退回较弱模式。

## 9. 结论边界

本报告不按用户给出的热度数字排名，也不宣称某仓库在真实任务上“更遵从”。它证明的是固定提交中的代码路径、局部默认与明显旁路。最有价值的横向发现是：五仓已经大量尝试让 agent **看见**指令、**产生可解析动作**和**在出错后停止**，但“每个副作用都必须在执行前通过统一、不可绕过、fail-closed 的指令一致性裁决”仍未在任一固定提交中成立。
