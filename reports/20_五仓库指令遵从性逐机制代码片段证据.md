## 1. 目的与核验口径

19 号报告给出了机制、调用路径、形式化分类、默认/错误语义和旁路。本报告进一步回答：这些结论是否能在固定提交中找到**逐字、带行号、可独立复核**的代码证据。

每个机制至少核验四类证据：

1. **实现/入口：**机制被装配或调用，而不只是文档中出现；
2. **裁决/sink：**允许、拒绝、过滤、执行、保存、发送或恢复的决定性分支；
3. **默认/边界：**默认开关、异常降级、直接调用或外部执行边界；
4. **测试：**仓库内是否有真实断言覆盖该局部性质；没有则明确记录测试缺口。

代码块均来自下列固定提交，路径均为仓库根目录相对路径。片段只保留证明主张所需的最小上下文；省略号不替代决定性条件分支。

### 1.1 如何处理“未发现”类主张

“没有统一策略层”“没有 sandbox”“没有针对性测试”不能由一段代码直接证明。本报告对这类负命题采用三联证据：

1. 在 18 号实验记录中保留全仓查询族与 sink 反向追踪范围；
2. 展示最接近该控制的真实执行入口，证明它实际只检查了什么；
3. 列出已检查的替代入口/测试位置和未覆盖性质，把结论限定为固定提交与已审计路径下的“未发现”，不写成跨版本绝对不存在。

因此，代码片段能直接证明 `if/else`、默认值、调用顺序和副作用入口；它不能单独证明 LLM 实际遵从率，也不能把仓库边界外的实现当作已经核验。

## 8. 发现的证据缺口与报告修正

### 8.1 不能由当前仓库闭合的证据

- **OpenHands OH-1～OH-5：**当前仓只拥有 Canvas payload、UI confirmation 与 orchestration；canonical action dispatcher、风险绑定和真实执行阻断在外部 `software-agent-sdk`/server。因此这些机制有详细协议片段，但不是 server-side 完整调解证据。
- **外部 provider/MCP：**Cline CL-5 能证明本地 runtime 不执行 provider tool，也能定位 MCP wrapper 的 `provider.callTool` sink；无法据此证明外部服务实际做了什么。
- **负命题：**AutoGen 未发现危险命令 sanitizer、MetaGPT 未发现统一授权层等结论，依赖 18 号报告记录的查询族、sink 反向追踪与最接近入口，而不是把一次 `rg` 零命中当作绝对证明。
- **行为效果：**所有代码片段只证明静态结构和仓库内测试意图，不能证明模型在真实任务中的遵从率、外部服务语义或本轮测试已实际通过。

### 8.2 有实现但缺少同强度针对性测试的项目

| 机制 | 缺口 |
|---|---|
| OH-4 | 没有当前仓库内 action binding、mutation 失败回滚或 TOCTOU 测试 |
| BU-1 | prompt 装配有实现，测试主要覆盖 schema/flash 字段，没有指令优先级断言 |
| BU-9 | judge 调用存在，测试只覆盖 self-report/trace telemetry，没有 verdict 支配断言 |

### 8.3 复核后对 19 号报告作出的实质修正

1. **MetaGPT MG-1：**`max_loop` 只在 `total_cost < 1` 的分支生效，不再写成无条件循环上限。
2. **MetaGPT MG-4：**`raw` 模式显式跳过 structured model；single/code/XML 路径最终仍可形成 Pydantic 对象，但绕开标准结构解析，已区分这两种语义。
3. **MetaGPT MG-5：**`redo` 分支本身只是 `pass`，重做来自外层 planner loop 的隐式再次执行。
4. **MetaGPT MG-7：**`"LGTM" in result` 会把 `NOT LGTM` 也视为通过；循环结束仍无条件写最后版本。
5. **browser-use BU-5：**上传允许集被修正为 available、downloaded 与 managed 文件的并集；`external_file` 的读取绕过 managed path，remote path 也不能外推为本地 containment。
6. **browser-use BU-7：**beta agent 测试证明的是 adapter/parity，不是 canonical agent loop 的等价集成覆盖。
7. **AutoGen AG-5：**Docker `containers.create` 未显式关闭网络，只能得出“没有代码级断网保证”，不能断言容器默认一定联网。
8. **Cline CL-3：**heredoc body 会被屏蔽，但 heredoc 的文件重定向仍会检查；已删除“所有 heredoc 写入均绕过”的过强表述。
9. **Cline CL-4：**`afterTool` 可以 stop，但发生在副作用之后，只能约束后续轨迹。
10. **Cline CL-5：**provider 分支只证明本地不执行，不能证明外部 provider 已经成功完成动作。
11. **Cline CL-6：**abort 只尝试 Ctrl+C，没有进程树级 kill 保证。

## 9. 核验结论

本轮逐一复核了 **35 个机制**：OpenHands 7 个、browser-use 9 个、AutoGen 6 个、Cline 6 个、MetaGPT 7 个。结论是：

1. **每个机制现在都有详细代码证据。**至少包含一个真实实现/入口片段，并给出决定性条件、sink、默认或旁路的行号；不再有只凭功能名、README 或二手描述成立的机制条目。
2. **并非每个更强性质都有闭合证据。**OpenHands 的 server-side 强制、Cline 外部 provider 行为、若干“未发现”负命题和上表测试缺口仍被显式降级为“外部边界”或“部分”。
3. **最强静态证据仍是局部支配关系。**AutoGen code approval、Cline local AgentTool approval、browser-use navigation/file gate 等仅在限定 sink 与配置下成立；不能推广为所有副作用都满足自然语言指令。
4. **报告之间已一致化。**19 号报告的机制定义、默认语义与旁路已按本次逐字复核修正；本报告保存可复核片段，18 号报告保存查询与实验轨迹。

所以，对“当前产出中的每一处是否都有详细代码证据”的准确回答是：**35 个机制层面的核心判断均已有逐机制代码片段；但仓库外执行、负命题和缺少专门测试的局部性质不能宣称为完全证明，报告已逐项标明证据等级与边界。**
