### 1.1 获取异常与处理

- 五仓首次并行浅克隆时，AutoGen 与 Cline 在 Git for Windows 检出阶段出现 `couldn't create signal pipe, Win32 error 5`；Git 对象已经下载，但工作树不完整。
- Cline 在沙箱外顺序恢复后有 3,864 个受控条目，唯一 Git LFS 文件是 `assets/docs/demo.gif`；该演示资产与源码审计无关。
- AutoGen 的部分检出同时留下索引/工作树不一致。经解析并验证目标绝对路径严格等于工作区 `tmp/five_repo_instruction_compliance/autogen` 后，只删除该临时副本并顺序完整重拉；最终受控文件数与实际文件数均为 1,837。
- 其余三个仓库一次检出完成。所有正式结论只使用最终固定工作树。

## 2. 资源探针与分析策略

按计算任务资源技能运行 `detect_resources.py`。脚本首先因 Windows GBK 终端无法编码 emoji 失败；改用 Python UTF-8 模式后，又因本机 `psutil.disk_usage()` 在 Windows 路径上抛出 `SystemError: argument 1 (impossible<bad format char>)`，导致其推荐生成器访问不到 `disk.available_gb`。这是资源检测工具兼容性失败，不是目标仓库失败。

回退到只读系统探针得到：

| 资源 | 观测值 | 对实验的影响 |
|---|---:|---|
| 逻辑处理器 | 20 | 文本搜索可并行，但没有必要把全仓 AST 同时驻留内存 |
| 物理内存总量 | 15.73 GB | 中等规模 |
| 探针时可用内存 | 1.96 GB | 采用逐仓、流式 `git grep`/`rg`，不做多进程全仓 AST |
| D 盘剩余空间 | 185.76 GB | 足够保存五个浅克隆 |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU，8,188 MiB | 静态代码分析不使用 GPU |

由于可用内存偏低，五仓候选搜索逐仓进行；只有相互独立、只读、不会争用文件写入的人工代码审计交给独立 worker。第三方工作树、命中缓存、worker ledger 和临时资源信息均留在 `tmp/`，不作为长期交付物提交。

## 3. EXP-2：统一候选召回

### 3.1 查询族

对每个固定仓库的**受版本控制文本**使用 `git grep -I -i -n -E`，排除二进制和未跟踪产物。五个查询族与协议一致：

```text
Instruction   = instruction|system[_ -]?prompt|policy|rule|constraint|priority|override
ToolApproval  = tool[_ -]?call|permission|approv|allow|deny|confirm|human.?in.?the.?loop
Validation    = schema|validat|saniti[sz]|guardrail|invariant|postcondition
Execution     = sandbox|container|workspace|path traversal|network|shell|command
RecoveryAudit = retry|replan|terminat|stop|event|trace|audit
```

“命中行”是一行至少命中一次，“命中文件”是至少有一行命中的唯一受控文件。查询族有重叠，不能相加成唯一候选数量。

## 4. EXP-3 至 EXP-6：从候选到机制的核验步骤

实际执行采用以下顺序：

1. 用 `rg --files` 和目录树定位 agent loop、prompt/context、tool registry/dispatcher、approval UI/API、runtime/sandbox、browser/file/network sink 与测试目录；
2. 从关键词命中前向读取构造函数、调用者、分派器、默认配置和异常分支；
3. 从真实副作用 sink 反向检查是否经过候选 gate；
4. 对动态 schema、配置映射与 UI 机制检查“生成时限制”和“执行时重检”是否为同一层；
5. 搜索测试中对目标符号的实际调用与断言，不以测试文件名授予 E2；
6. 用 `g=(L,T,X,Q,D,F,B,E)` 编码；缺失字段会触发再次检查或降为边界项；
7. 对高风险措辞执行反事实检查：删除或绕过该代码是否扩大与指令约束有关的可达动作集合；若只是改变模型概率，则只标 `INDUCE`。

### 4.1 特别边界：OpenHands 的仓库重构

固定版本的 `OpenHands/OpenHands` README 与 `AGENTS.md` 明确说明：该仓库当前只拥有 Agent Canvas React/TypeScript 前端、后端选择和本地栈编排；Python agent、工具、conversation、workspace、event 与 Agent Server API 的真正实现位于外部 `OpenHands/software-agent-sdk`。因此：

- 本报告可以证明 Canvas 如何构造 `confirmation_policy`、`security_analyzer`、tools、skills、worktree、max iterations 等请求，以及如何显示并提交确认；
- 本报告不能仅从本仓库证明 server 在每个副作用前强制执行这些请求；
- README 中 Docker/Cloud 的隔离说明只作架构边界，不能替代外部 SDK 的代码证据；
- 本地 npm/source 启动路径明确警告 agent server 直接在主机运行、拥有完整文件系统访问；git worktree 是变更隔离，不是 OS 安全沙箱。

这是版本事实，不沿用旧版 OpenHands 单仓架构的印象。

## 5. 仓库原生测试探针

本轮以静态分析为主，E2 表示固定仓库内存在到达机制且有有效断言的测试，不要求本机执行通过。仍进行最小环境探针，以区分“可执行”和“只读到测试”。

### 5.1 browser-use

尝试运行：

```text
python -m pytest tests/ci/security/test_domain_filtering.py
  tests/ci/security/test_sensitive_data.py
  tests/ci/security/test_upload_file_containment.py
  tests/ci/security/test_download_filename_sanitization.py -q
```

收集阶段在 `tests/ci/conftest.py` 导入时停止：`ModuleNotFoundError: No module named 'pytest_httpserver'`。因此没有任何目标测试被执行，结果记为**环境依赖缺失**，不是测试失败。静态 E2 仍需逐条读取断言确认。

### 5.2 OpenHands

工作树没有 `node_modules`，本机 Node 为 `v20.20.2`，而仓库 README 要求 Node 22.12 或更高。没有为静态审计额外安装数千个 npm 依赖，也没有运行 Vitest；对应测试只作静态 E2。

### 5.3 AutoGen、Cline、MetaGPT

没有安装各仓库完整语言与服务依赖，也没有声称运行全量测试。逐机制测试锚点的 E2 只表示仓库内存在针对性测试和断言；动态复现列统一保持“未执行”。

## 6. 证据抽取和一致性规则

最终证据矩阵的每一行包含：

```text
repository, commit, mechanism_id, mechanism,
implementation_anchor, call_path_or_sink,
L, primary_mode, target, trusted_owner, state,
decision, failure_semantics, default,
bypass_or_limit, test_anchor, evidence_level
```

一致性规则：

- `AUTHORIZE` 必须能形成 `allow/deny/ask`，提示中的“不要”不能编码为授权；
- `ISOLATE` 必须限制真实能力或资源，git 分支/工作树只编码为协作隔离；
- `VALIDATE` 必须说明在副作用前还是后；
- 只在模型 schema 中隐藏工具、但执行器仍接受直接调用的机制，标为生成约束而不是完整强制；
- post-hoc judge、trace、reward 或 UI 警告不能升级为阻断；
- 默认关闭、无规则放行、解析失败放行、错误降级和直接 API 入口必须进入 `F` 或 `B`；
- 静态“未发现”只限定于固定提交和已查调用路径，不表述成全版本绝对不存在。

## 7. 实际协议偏差与有效性威胁

1. **浅历史：**无法分析机制何时引入、过去默认值或历史漏洞修复范围。
2. **外部依赖：**OpenHands 的强制层在独立 SDK；AutoGen/MetaGPT/Cline 也可调用外部模型、shell、浏览器、MCP 或扩展，仓内静态审计不能证明外部系统语义。
3. **运行时缺失：**没有统一模型、浏览器、容器、OS、凭据和网络环境；不比较真实成功率或攻击成功率。
4. **多语言：**同一仓库内可能有 Python、TypeScript、C# 或生成协议代码；抽取按行为而不是按类名统一，但仍可能漏掉反射/动态注册路径。
5. **测试选择：**E2 是仓库作者测试，未运行且不是独立复现；断言覆盖的局部性质不能外推为完整调解。
6. **关键词召回：**五族查询偏向英文命名；通过副作用 sink 反向追踪和重要负例记录降低漏检，不能消除。
7. **当前资源压力：**低可用内存使扫描逐仓串行；不会改变语义，但增加了人工抽取时间。

## 8. 可复现结论范围

本实验能够支持：固定提交中某机制及调用路径存在；配置默认/异常分支的静态语义；仓库内是否有针对性测试；控制是在提示、生成、执行前、执行中或执行后；明显旁路或跨仓边界。

本实验不能单独支持：某项目“更遵从”；任一控制在所有部署中不可绕过；LLM 实际遵从概率提升；外部服务与插件无隐藏入口；用户给定热度与机制质量相关。

## 9. 子审计复核与终态

AutoGen、Cline、MetaGPT 的独立只读审计分别由 `/root/audit_autogen`、`/root/audit_cline`、`/root/audit_metagpt` 完成；三者均固定到表 1 的 commit，未修改第三方 checkout，并在主报告合并前进入 `completed` 终态。主线程对高风险结论作了如下抽查：

- AutoGen：确认 `CodeExecutorAgent` 默认 `approval_func=None` 会继续执行，配置序列化禁止携带 callback，`_from_config` 恢复为 `None`；
- Cline：确认 local tool 的 hook→policy→approval→execute 调用顺序、无审批 callback 时 fail-closed，以及 provider execution branch 不进入本地执行；路径证据的实际文件位于 `extensions/tools/executors/`；
- MetaGPT：确认 `write_framework` 在更新 `is_pass` 后仍无条件调用 `save_framework`，RoleZero 只按 `tool_execution_map` 名称调度，以及 Terminal 黑名单覆盖极窄；
- OpenHands、browser-use 由主线程直接完成入口—sink 追踪；browser-use 的选定测试因缺少 `pytest_httpserver` 在收集阶段停止，OpenHands 因 Node/依赖条件未运行测试。

所有 E2 结论均只表示固定提交内已有真实断言；没有动态执行的项目不写作“测试通过”。临时 checkout 与 worker ledger 不属于长期交付，正式可复现信息已完整转录到本文件和最终证据报告。
