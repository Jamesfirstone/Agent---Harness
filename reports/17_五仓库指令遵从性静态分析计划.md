# 五个开源 Agent 仓库的指令遵从性静态分析计划

日期：2026-08-29
状态：已启动；本文件是预先持久化的研究协议，后续结果不反向修改纳入标准，只补记实际偏差。

## 1. 研究对象与目标

本轮审计以下五个用户指定仓库；括号内数字是用户提供的抽样时点热度信息，不作为质量或效果证据。

| 项目 | 用户给定数字 | 预期上游仓库 |
|---|---:|---|
| AutoGen | 60,507 | `microsoft/autogen` |
| Cline | 66,458 | `cline/cline` |
| MetaGPT | 69,892 | `FoundationAgents/MetaGPT` |
| OpenHands | 84,457 | `All-Hands-AI/OpenHands` |
| browser-use | 109,703 | `browser-use/browser-use` |

目标不是统计含有 `guardrail`、`policy` 等词的文件，而是识别真实参与 agent 指令进入、解释、计划、动作执行、结果验证与恢复的代码机制，并回答：这些机制在哪个生命周期阶段生效、由谁执行、以什么方式改变可达行为、失败时是否放行、是否具有可绕过路径，以及仓库内证据能支持到何种强度。

## 2. 研究问题

- **RQ1（存在性）：**每个仓库中有哪些以代码实现、并对指令遵从有直接作用的机制？
- **RQ2（语义）：**每个机制接受什么输入、维护什么状态、产生什么裁决或状态转换？
- **RQ3（位置）：**机制位于指令生命周期的哪个阶段，是否支配真实副作用？
- **RQ4（作用方式）：**机制属于提示塑形、结构约束、权限裁决、执行隔离、人工批准、后置验证、恢复控制、审计反馈中的哪一类？
- **RQ5（保证边界）：**默认值、异常、超时、配置关闭和旁路情况下的语义是什么？静态证据最多支持何种保证？
- **RQ6（跨仓库比较）：**五个仓库的控制链覆盖、组合方式和薄弱环节有何异同？

## 3. 操作性定义与形式化框架

把一次 agent 运行建模为带标签转移系统：

\[
\mathcal H=(S,I,C,P,A,O,\delta,\Gamma),
\]

其中 \(S\) 是运行状态，\(I\) 是用户、系统、仓库或环境指令集合，\(C\) 是由指令解释出的约束，\(P\) 是模型提出的计划或调用，\(A\) 是具有潜在外部效果的动作，\(O\) 是观察，\(\delta\) 是状态转移，\(\Gamma\) 是 harness 实现的控制机制集合。

对机制 \(g\in\Gamma\)，统一记录为：

\[
g=(L,T,X,Q,D,F,B,E),
\]

- \(L\)：生效生命周期阶段；
- \(T\)：受控对象（消息、计划、工具、参数、资源、结果或会话）；
- \(X\)：可信执行主体（模型、harness、沙箱、人工或外部服务）；
- \(Q\)：跨步状态；
- \(D\)：裁决集合，如 `allow/deny/ask/transform/retry/terminate`；
- \(F\)：失败语义，如 fail-open、fail-closed、降级或未知；
- \(B\)：已识别旁路集合；
- \(E\)：证据等级。

若 \(Exec(a)\) 表示动作产生真实副作用，\(Allowed(a,s,C)\) 表示动作在状态 \(s\) 和约束 \(C\) 下被授权，则“前置强制遵从”的必要条件写为：

\[
\forall a,s:\ Exec(a)\Rightarrow Mediate(a,s,C)\land Allowed(a,s,C).
\]

仅修改提示或在执行后记录违规不满足该必要条件，因此分别标为**行为诱导**与**检测/反馈**，不能静态推断为强制保证。

### 3.1 生命周期编码

| 编码 | 阶段 | 典型对象 |
|---|---|---|
| L0 | 配置与策略装载 | system prompt、规则、权限、运行模式 |
| L1 | 指令摄取与规范化 | 消息、上下文、来源标签 |
| L2 | 上下文构造与优先级 | prompt 拼接、历史裁剪、规则注入 |
| L3 | 计划/输出生成约束 | schema、grammar、终止条件 |
| L4 | 工具选择与参数验证 | tool allowlist、参数 schema、路径/命令检查 |
| L5 | 执行前授权 | 人工批准、策略 gate、风险裁决 |
| L6 | 执行与隔离 | sandbox、容器、文件/网络/进程边界 |
| L7 | 结果与后置条件 | validator、结果过滤、任务完成判定 |
| L8 | 恢复、终止与审计 | retry、replan、rollback、事件日志 |

### 3.2 作用方式编码

`INDUCE`（提示/上下文诱导）、`CONSTRAIN`（结构化生成或参数约束）、`AUTHORIZE`（确定性或人工裁决）、`ISOLATE`（能力/资源隔离）、`VALIDATE`（执行前或执行后验证）、`RECOVER`（受约束恢复/终止）、`AUDIT`（可追溯记录）、`EVALUATE`（离线测量）。同一机制可多标签，但必须指定主要标签。

### 3.3 证据等级

- **E0：**仅文档、注释或提示文本声称；
- **E1：**存在可追踪的实现和调用路径；
- **E2：**仓库内有针对该路径的测试；
- **E3：**有对照、消融或行为测量；
- **E4：**本轮独立动态复现或生产证据。

本轮以静态分析为主，原则上只给 E0–E2；除非确实执行针对性实验并保存输入、输出和环境，否则不授予 E4。

## 4. 纳入与排除标准

### 4.1 纳入

候选代码必须满足至少一项：

1. 改变模型能看到的指令、规则、工具或上下文；
2. 限制模型输出、工具选择、参数、资源或副作用；
3. 在动作前形成 allow/deny/ask/transform 裁决；
4. 隔离执行能力或限制文件、网络、进程等资源；
5. 检查结果、完成条件或违规，并驱动重试、重规划或终止；
6. 记录足以重建指令—决策—动作链的结构化事件；
7. 以测试或评测直接测量上述机制。

### 4.2 排除

- 只在 README、营销文案、示例 prompt 或 issue 中出现而无实现路径；
- 通用鉴权、日志、类型检查或错误处理，且与 agent 指令或动作控制无可追踪关系；
- 单纯模型安全过滤，未进入目标仓库的 agent 控制流；
- 重复封装、生成文件、vendor、构建产物和快照；
- 只提高任务能力而没有可辨识约束语义的普通规划或记忆代码。

边界对象不直接删除，先标为“待定”，再根据调用图和反事实问题裁决：移除该机制是否会扩大与指令约束有关的可达行为集合？

## 5. 静态分析协议

### 阶段 A：版本与本地性审计

1. 检查 `repos/`、Git 子模块和既有报告，优先复用完整本地副本；
2. 对缺失仓库从预期上游拉取，只保存 Git 来源、分支、提交、日期和工作树状态；
3. 记录浅克隆、LFS、子模块、大小写或 Windows 路径限制；
4. 不把星标数作为代码证据，也不在分析中自动更新固定版本。

### 阶段 B：全仓候选发现

对所有受版本控制文本执行可复现搜索，查询族至少覆盖：

- 指令与优先级：`instruction|system prompt|policy|rule|constraint|priority|override`；
- 工具与批准：`tool call|permission|approve|allow|deny|confirm|human-in-the-loop`；
- 结构与验证：`schema|validate|parse|sanitize|guardrail|invariant|postcondition`；
- 执行边界：`sandbox|container|workspace|path traversal|network|shell|command`；
- 恢复与审计：`retry|replan|terminate|stop|event|trace|audit`。

先按目录和文件类型生成命中分布，再以框架入口、agent loop、tool executor、runtime/sandbox、审批 UI/API、测试目录为种子追踪调用关系。关键词只用于发现，不直接计为机制。

### 阶段 C：调用路径与反事实核验

每个候选至少回答：入口在哪里；由谁调用；裁决是否能支配副作用；默认/错误分支是什么；配置是否默认启用；是否存在未经过该入口的执行路径；相关测试刺激是否真正到达该机制。使用文本搜索、符号引用、配置默认值、测试引用和必要的轻量 AST/语法查询进行核验。

### 阶段 D：统一抽取

每条纳入机制写入证据表：`repo/commit/机制名/代码锚点/调用链/L/T/X/Q/D/F/B/作用方式/默认启用/测试锚点/E级/研究备注`。代码锚点采用仓库相对路径和符号名；最终报告同时给出固定提交，避免行号漂移造成伪精确。

### 阶段 E：负例与完整性检查

1. 对高频但排除的候选保留负例及排除理由；
2. 从真实副作用 sink 反向追踪，检查 shell、文件、浏览器、网络、MCP/插件等入口是否全部经过已识别 gate；
3. 单独检查异常、超时、解析失败、未知工具、配置关闭和直接 API 调用；
4. 将“存在控制组件”与“完整调解”分开编码。

## 6. 实验与可复现产物

计划产生以下长期交付物：

1. 本计划文件；
2. 固定版本清单与获取限制；
3. 全仓候选搜索查询、命中统计和负例日志；
4. 五仓库逐项证据矩阵；
5. 形式化机制定义与跨仓库分类报告；
6. 必要时保存可复用的只读扫描脚本，但不保存一次性缓存或完整第三方仓库内容。

实验按以下顺序执行：

- **EXP-1 本地性与版本实验：**确认是否已存在、能否完整读取、固定 `HEAD`；
- **EXP-2 候选召回实验：**统一查询族扫描五仓库，形成目录/关键词族分布；
- **EXP-3 控制路径实验：**从候选到入口与副作用 sink 双向追踪；
- **EXP-4 默认与故障语义实验：**静态枚举配置、异常和回退路径；
- **EXP-5 测试证据实验：**映射机制到仓库内测试与断言；
- **EXP-6 形式化编码实验：**使用 \(g=(L,T,X,Q,D,F,B,E)\) 双重检查每条机制；
- **EXP-7 跨仓库分类：**按生命周期、作用方式、决策主体、状态性、默认启用和保证强度比较。

## 7. 验收标准

- 五个仓库都有固定来源和提交；无法获取者有明确失败记录；
- 每个纳入机制至少有一个实现锚点和一条可解释调用路径，E2 必须另有测试锚点；
- 每个仓库同时记录纳入项、重要排除项、默认/异常语义和已知旁路；
- 所有强制性表述都经过副作用支配关系检查；
- 分类表能回溯到逐仓库证据，而不是只给抽象标签；
- 研究方法、命令/查询族、偏差、限制与实际协议偏差均写入 `reports/`；
- 最终变更通过 Git 差异复核，只提交本任务长期交付物，不纳入第三方仓库、缓存和用户已有改动。

## 8. 预期偏倚与控制

- **关键词偏倚：**用副作用 sink 反向追踪补充纯关键词召回；
- **语言/架构差异：**以行为语义而非类名统一编码；
- **文档夸大：**E0 不升级为实现证据；
- **测试存在偏倚：**检查断言和调用路径，不以测试文件名直接授予 E2；
- **版本漂移：**所有结论绑定固定提交；
- **研究者判断偏倚：**保留边界项、负例和排除理由，并对形式化字段做一致性复核；
- **静态分析局限：**静态可证明“路径存在/可能绕过”，通常不能证明运行时效果、模型行为改善或生产环境无旁路。
